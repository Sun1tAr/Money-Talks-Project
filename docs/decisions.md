# Инженерные решения Money Talks Project

## Микросервисная декомпозиция

Пользователи, счета, категории и операции разделены на самостоятельные сервисы,
чтобы бизнес-правила и изменения данных не концентрировались в одном приложении.
Взаимодействие — только по HTTP, без общей шины и распределённых транзакций.

## Контекст пользователя вместо сессий

Gateway аутентифицирует клиента по JWT и передаёт в сервисы доверенный заголовок
`X-User-ID`. Сервисы не разбирают токен и не хранят сессии: `RequestInterceptor`
из `commons` кладёт идентификатор в MDC, а `RequestContextService` отдаёт его
бизнес-коду. Клиентский заголовок `X-User-ID` срезается на входе.

## Надёжность межсервисных вызовов

Gateway и сервисы используют typed clients (OpenFeign), fallback-обработчики и
Resilience4j. Fallback возвращает доменную ошибку с заголовком `X-Error-Code`,
поэтому вызывающий код явно отличает ошибку домена от недоступности зависимости.

## Повторное исполнение ордера

Ордер создаёт Transaction Service, а балансы меняет Account Service. Ордер имеет
собственный UUID и статусы `CREATED`, `EXECUTING`, `EXECUTED`, `UNREGISTERED`.
Пересчёт балансов выполняется в транзакции `SERIALIZABLE`: ордер сохраняется, затем
пересчитываются суммы. Если ответ потерян, Transaction Service опрашивает статус:
`EXECUTED` — операция завершена, `UNREGISTERED` — ордер отправляется повторно,
`CREATED` — опрос повторяется. Повторный запуск для транзакции в статусе
`EXECUTED` отсекается на стороне Transaction Service; сам Account Service проверку
статуса не выполняет, поэтому его эндпоинт не является идемпотентным.

## Схема на сервис

Все сервисы работают с одной базой `mtp_dev`, но каждый — в своей схеме
(`mtp_user`, `mtp_accs`, `mtp_category`, `mtp_transes`). Схемы создаются заранее;
Liquibase управляет таблицами и данными внутри схемы.
